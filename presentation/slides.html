Circling back around though, what was GetThru's problem? What pain points were we seeing? Because every module was responsible for subscribing and broadcasting directly, there was no reasonable way to find what our pub/sub API was. There was no way to easily see what the name of a topic is. No way to keep topic naming consistent. No way to keep event naming on those topics consistent. No way to keep the shape of the payloads for those events consistent. And, at another level, we hadn't defined what our expected behavior was for subscribers. If a process subscribes to a topic, does it have to have an explicit handler for every possible event? What happens if unexpected events are sent? Is it ok to have a catch-all handler? If so, what should the behavior of that handler be? Should it log a warning? Should it raise and crash the process? Nobody knew. Nobody had decided what the behavior should be, so it was a combination of all of those. There was no consistency.

Going down that path with our TexMex app, here you can see how we broadcast tickets to kitchen stations. An order comes in and each line item is sent to appropriate kitchen station.

Each kitchen station then subscribe to the topic for their station

and handles the event with handle_info. This about the most basic way to do pub/sub in an Elixir app. Just call the raw functions. And this can be fine! If your app is small, then you don't need any more complexity. But when your app is larger, then this becomes unwieldy. It becomes difficult to keep track of your API for pub/sub. What topics does your app use? What is your preferred naming pattern for topics? What conventions do you want for the shape of payloads? What about the weight of payloads? Answering those questions is harder unless you start centralizing your management of pub/sub The first thing we did to start addressing these issues was to start centralizing pub/sub subscribe and broadcast functions in a single module. This started making it easier to understand what pub/sub the app was even doing. We started doing this work in 2024. These days it would be pretty easy to use your LLM of choice to have one big PR that made a cross-cutting change across the app to centralize all the subscribe and broadcast functions. This was difficult to spot before. It was extremely rare for more than one of these to open at the same time and see this uncommon event be published. Because of that, it was never a priority to dig into our error tracker and figure it out.

Verified routes derives valid routes through the router module.

Phoenix PubSub has no equivalent module to organize topics and messages, so we have to make our own. Enter the manifest module Manifest here means something like a shipping manifest. A shipping manifest lists everything and everybody on a ship. Here, we want to list all the topics, the messages on those topics, and the shape of the payload for those messages. Not quite a 1:1 mapping on to a shipping manifest, but the name works well enough.

Looking at the topic we have here, the first atom is a unique name for your topic. This is not the shape of the topic on the wire. That part is defined by the list. So, the topic on the wire ends up becoming something "tables:42", "tables:7", etc. This DSL uses Spark. It gives us the equivalent of a router module for pub/sub. This lets us gather metadata for what every topic and message looks like, including the shape of the payload of each message.

How do we use it though? I strived to make the API pretty similar to phoenix_pubsub, deviating only where it made sense. We call broadcast with or without a bang. The :table atom matches the name of the topic in the manifest. The table_id is interpolated into the topic name, so we get something like "tables:42" again. After that is the name of the message, :placed in this case. Finally, there is the payload of the message itself. The manifest says the message has order_id and line_items fields.

Just like phoenix_pubsub, you can also call broadcast_from, with or without the bang.

How do we subscribe to these topics though? It looks pretty much like you would expect. We subscribe to the :table topic. A map is passed just like when broadcasting to fill in the table_id. You get back an :ok atom on success, just like phoenix_pubsub.

Handling messages looks different though. Instead of handle_info, we use a handle_broadcast macro. Here we see an example of handling the :ready event on the :table topic. This message has an order_id, which we pattern match. Now, I talked earlier about a philosophical disagreement on the team about how we handle unexpected events on a topic. verified_pubsub makes the choice that every message must be explicitly handled or ignored. You can choose to ignore with ignore_broadcast

In this example, we can see this live view subscribes to a couple of topics that have messages we don't actually care about. We must explicitly handle or ignore every message on a topic.

Now we get to the fun parts. The library is called verified_pubsub, but what can we actually verify with this? The manifest lets us do a lot. We can verify that the topic exists.

We can verify that the topic is given the correct params to be built.

We can verify that the message we're broadcasting exists in the manifest

We can verify that the payload of the message has the correct shape.

We can verify that you subscribing to a topic that exists in the manifest

We can verify that you've passed the correct params to build the topic.

What if you don't handle a message on a topic? Compilation error A recurring pattern we see these days is that tools that are good for humans are also good for LLMs. This is yet another example. This validation is useful for both human and robot.

One thing we also struggled with previously was finding out where and how pub/sub was being used. Centralizing usage of pub/sub to a single module helped, but this helps a lot more. Robots are great with grep, but we can do better than that. We already have a manifest and a boatload of macros. What if we tracked metadata about usage of pub/sub at compile time to give us something like `mix phx.routes`?

We can do that with `mix verified.pubsub.topics` This mix task gives us all the topics in the app, where they are subscribed to, and a breakdown of usage of all the messages on each topic. We can see where each message is broadcast, handled, and ignored. You and the robot don't have to grep through your code anymore. The metadata is right there.

And you can filter it as well. If you want to see all the usage of a particular topic, pass the name of the topic.

Or you can get really fine grained and filter it by just the event on the topic as well.

Or maybe you want something a little more machine readable. You can get the results as unformatted json as well. Just pipe it into jq or your favorite tool for additional munging.

Does all of this have any performance cost? At runtime, no. The only check that cannot be done at compile time is the types on fields in a message These types must be checked at runtime. That's pretty low.

You can see here that we're talking about microseconds. Now, if you start broadasting large lists over pub/sub, that does get into hundreds of microseconds, but that is not a use case that I have seen. I haven't worked on an app that sends messages that heavy. There is a hit on compilation times though.

You can see the entire cost is in the manifest. Editing the manifest is going to cause a recompilation penalty. I'm fine with that tradeoff. You can also see that the performance is not good as the number of topics in a single manifest grows. The library does support multiple manifests, but we haven't gotten to the point of using that at work yet. There will probably be refinements if/when we use it. Benchmarks like this are trivial to run now. With LLMs, there is no excuse to not be setting up benchmarks on your apps and libraries. I told Claude I wanted run and compile time benchmarks. 15 minutes later I had benchmarks that were good enough for my purposes. It actually pushed the library way further than I think is reasonable. The first benchmarks went up to 1,000 topics. Each topic had 5 events with 5 fields each. That is a lot. Even the 250 topics I settled on for the upper bound is a lot.

This led me to upgrade Spark because Zach Daniel had thrown the robot at Spark performance in the weeks since I had started working on the library. The big win was reducing the size of the .beam file from 18 -> 3.6 MB on the 250 topic case.

Where do we go from here? This library is in production at work. It is not being used everywhere yet. I'll continue to refine the library as I port the rest of our usage. We're consistently finding bugs and inconsistent usage as we port the legacy pub/sub. That is the part that takes the most time. We continue to run into topics and messages with inconsistent shapes. It's very clear that there were no guiding principles here. I expect the API to be a bit in flux as that happens. I think the core is pretty set now, but edge cases will come up that need to be addressed. For example, while putting together this demo app a case came up that we could verify at compile-time that the library didn't support yet. This is a topic for stations in the kitchen. The list of stations is a list of atoms known at compile-time. It could be a compile-time error if you try to use value not in that list for :station. I haven't ported anything like this in our app yet, so I haven't gotten to it.
